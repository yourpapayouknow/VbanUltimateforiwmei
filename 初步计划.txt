你现在接手一个全新的 macOS 音频工具项目。

项目目录已经创建，项目名：

vbanultimateforiwmei

你的任务不是做 Demo，而是从现在开始把它作为一个可长期维护、最终可日常稳定使用的 macOS 原生音频工具进行设计和实现。

====================
一、项目目标
====================

我要开发一个面向 macOS 的轻量、高性能 VBAN 音频工具，最终目标可以概括为：

“VBAN Matrix + VBAN Talkie + 动态虚拟音频线缆管理器”

但必须严格控制功能范围，不要发展成 DAW、Voicemeeter、Splitwave 或复杂 DSP 软件。

核心只保留三类能力：

1. 完整的 VBAN 音频发送/接收与矩阵管理
2. macOS 虚拟音频设备/虚拟线缆创建和管理
3. VBAN Talkie 已有的完整状态、质量和指标监控能力

除此之外，不要主动加入：
- EQ
- Compressor
- VST/AU 插件
- 音效
- 文件播放器
- 系统录音
- App Capture
- ScreenCaptureKit
- 多轨编辑
- 复杂 Mixer
- DSP Graph
- 无关的音频工作站能力

软件首先是一个：
“VBAN 网络音频 + CoreAudio 虚拟线缆基础设施工具”。

====================
四、VBAN 功能
====================

这是项目最重要的一部分。

目标不是像 VBAN Talkie 一样只能接收一条 Stream。

必须从一开始设计为：

多发送 Stream
+
多接收 Stream
+
同时工作

网络层应该尽量做到：

单个 UDP Socket
        ↓
VBAN Packet Parser
        ↓
按 StreamName / Source 等信息进行分流
        ↓
多个独立 Stream Context

不要为了每个 VBAN Stream 启动一个完全独立的 Receiver 进程。

接收端至少支持：

- 多个 VBAN Audio Stream 同时存在
- 相同 UDP 端口上的不同 StreamName
- StreamName 筛选
- Source IP 筛选
- Source Port 信息
- Enable / Disable
- 自动发现新的 VBAN Stream
- 手动固定 Stream
- Stream 超时检测
- Stream 自动恢复
- PCM Audio VBAN
- 正确解析 VBAN Header
- Sample Rate
- Channel Count
- Bit Depth / Sample Format
- Frame Counter
- Stream Name

发送端至少支持：

- 多个发送 Stream
- 每路独立：
  - Stream Name
  - Destination IP
  - Destination Port
  - Source Audio Device
  - Channel Mapping
  - Sample Rate
  - Audio Format
  - Enable / Disable
- 同时向多个目标发送
- 同一个源可以创建不同发送 Stream

第一版重点保证 PCM Audio VBAN。

不要在第一阶段扩展：
VBAN MIDI
VBAN Text
VBAN Serial
VBAN Service

但 Protocol 层设计不要彻底堵死未来扩展这些类型的可能性。

====================
五、VBAN Matrix
====================

软件核心页面之一应该是 Matrix / Streams。

不要把它做成传统 DAW Mixer。

Matrix 的本质是：

Source
    ↓
Destination

Source 可以是：

- CoreAudio Physical Input
- Virtual Cable
- VBAN RX Stream

Destination 可以是：

- CoreAudio Physical Output
- Virtual Cable
- VBAN TX Stream

典型路线：

Mac Input
→ VBAN TX

Virtual Cable
→ VBAN TX

VBAN RX
→ Mac Speaker

VBAN RX
→ Virtual Cable

最终希望可以做到：

VBAN RX "PC-A"
→ "VBAN PC-A" Virtual Cable

VBAN RX "PC-B"
→ "VBAN PC-B" Virtual Cable

VBAN RX "Music"
→ MacBook Pro Speakers

BlackHole 不应该成为项目必要依赖。

====================
六、虚拟音频线缆
====================

这是第二核心模块。

目标是实现：

一个自己的 AudioServerPlugIn Driver
        ↓
由软件管理
        ↓
可以暴露多个独立 CoreAudio 虚拟音频设备

不要采用：

编译很多份 BlackHole2ch.driver

这样的方案。

目标应该更接近：

VBANUltimateAudio.driver

内部动态管理：

Virtual Cable A
Virtual Cable B
Virtual Cable C
Virtual Cable D

macOS Audio MIDI Setup 以及其他软件应该能看到这些独立设备。

例如：

VBAN - PC A
VBAN - PC B
VBAN - Music
VBAN - Talkback

优先研究：

Splitwave
libASPL
Apple AudioServerPlugIn API

重点只提取 Splitwave 的：

“虚拟设备创建、删除、命名、数据交换、生命周期管理”

相关思想或兼容源码。

不要搬入：

- Splitwave Router
- DSP
- App Capture
- Audio File
- Effects
- 其他节点系统

我们自己拥有 Routing Engine。

====================
八、虚拟设备的数据方向
====================

必须把 Virtual Cable 的方向设计清楚。

例如：

VBAN RX
→ Virtual Device

对于其他应用来说，这应该作为：

Input Device

被 OBS、Logic、Discord 等读取。

同时未来还需要：

App
→ Virtual Device
→ VBAN TX

也就是说虚拟设备最终应该支持完整的：

Virtual Output
→ Internal Buffer
→ Virtual Input

类似虚拟音频线缆。

请不要把“Input Device”和“Output Device”的 CoreAudio 语义搞反。

建立明确的数据流文档。

====================
九、实时音频要求
====================

音频线程必须遵守实时线程原则。

Audio callback 中禁止：

- malloc/new
- 文件 IO
- NSLog/大量日志
- Mutex 长时间阻塞
- 网络 DNS
- UI 操作
- JSON
- 动态容器频繁扩容

建议：

Preallocated Ring Buffer
Lock-free / wait-free where appropriate
Atomic counters

网络线程与 Audio Thread 之间通过：

Ring Buffer

交换 PCM 数据。

VBAN RX：

UDP
→ Parser
→ Jitter Buffer
→ Audio Ring Buffer
→ CoreAudio

VBAN TX：

CoreAudio
→ Ring Buffer
→ Packetizer
→ UDP

====================
十、网络时序处理
====================

不能简单做到：

收到 UDP 包
→ 立刻播放

必须设计基本的网络音频缓冲层。

至少考虑：

- packet loss
- duplicate packet
- out-of-order packet
- frame counter discontinuity
- jitter
- buffer underrun
- buffer overrun

第一版不要求复杂 PLC，
但不得因为单个 UDP packet 丢失导致整个 Stream 状态崩掉。

建立：

Jitter Buffer

并尽可能使延迟保持低且稳定。

目标优先级：

稳定
>
低延迟
>
极端低缓存
